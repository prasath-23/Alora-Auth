# Alora App Central (Go) — Architecture

Production architecture for **App Central**, Alora's identity provider. It is
where people sign in (password, Google or their company's SSO) and launch their
apps. It is the OpenID Provider every product's backend gets its own tokens from,
and the console where company Admins and the platform Owner manage access.

This document is the architectural contract. **`../SPEC.md`** holds the
exhaustive, byte-level behavioural and security invariants and the endpoint
inventory; where this doc summarizes, the spec governs.

- **Language/Runtime:** Go 1.26
- **HTTP:** Gin (`github.com/gin-gonic/gin`)
- **DB:** PostgreSQL via `pgx/v5` + `pgxpool`; type-safe queries generated by **sqlc**
- **JWT / JWK:** `github.com/lestrrat-go/jwx/v2` (RS256), for App Central's own tokens and for
  verifying Google's and company identity providers' ID tokens
- **Password hashing:** `github.com/alexedwards/argon2id` (argon2id)
- **Logging:** stdlib `log/slog` with a redaction handler
- **gRPC:** `google.golang.org/grpc`, for applications' tokens (`TokenService.GetToken`).
  The protos, their generated code and the Go helper that products and
  applications build against live in their own module, **`../alora-auth-go`**

## 1. Principles

1. **Five layers, with the features inside the core.** `internal/` holds:
   - `database` — every database call, organised by table;
   - `infrastructure` — SMTP, the OIDC client, background jobs;
   - `exceptions` — error sentinels and the envelope;
   - `middlewares` — the HTTP perimeter;
   - `core`.

   Each feature under `core/` owns a `controller/`, a `service/` and a `models/`
   folder, and nothing else; `core/shared` holds what several features need. A
   feature's blast radius stays local.
2. **All data access goes through `internal/database`, by table, not by
   feature.** One package per table under `database/services/` holds its CRUD
   (`<table>DbService.go`) and its custom queries (`customs/<table>DbCustoms.go`).
   Feature services call these. Nothing outside `internal/database` imports sqlc,
   and only test fixtures, which seed rows, touch the pool.
3. **Dependency direction points inward and downward.**
   `controller → service → table service → sqlc`:
   - controllers never touch the database;
   - services never touch a transport — neither `*gin.Context` nor gRPC;
   - the database layer never imports `core`.

   A service may call another feature's service, since business logic is
   reusable, but a controller never crosses features. No import cycles.
   Because the transports stay at the edges, HTTP and gRPC are two doors onto
   the same service methods: `/oauth/token` and `TokenService.GetToken` differ
   only in how the request arrives, so a rule added to the service holds at both.
4. **Thin controllers.** A controller binds and validates the request model,
   resolves its **scope** (below), calls its own feature's service with
   `c.Request.Context()`, and renders a response model. All branching,
   transactions, security decisions, audit and email live in the service.
5. **Every layer has its own model, and every boundary converts.**
   - `database/models` holds the table and view skeletons as plain Go types.
   - Each feature's `models/` holds its DTOs (`dto.go`) and its HTTP models
     (`request.go`, `response.go`).
   - The service converts skeleton → DTO, and `response.go` converts DTO →
     response.

   So a database model is never rendered, and a service never sees a request or
   response model.
6. **One company, two doors.** The same company-management controllers serve a
   company's Admins at `/api/admin/*` and the platform Owner at
   `/api/owner/companies/:cid/*`. A controller is built with a
   `shared.ScopeResolver`, which decides which company, which actor and whether
   the Owner is acting. Services take a `shared.Scope` and cannot tell the doors
   apart, so a rule is written once and holds for both. (A `shared.Scope` — who
   acts, on which company — is not an App Central scope such as `users:edit`,
   which is something the actor holds.)
7. **Fail closed.** Config validation, authorization, token verification, the
   same-origin check, the OIDC client and the Go helper's interceptors (a method
   without a rule is refused) all default to *deny* on error or ambiguity.
8. **Everything security-critical is compile-checked or test-pinned.** SQL is
   validated by sqlc at build time; behaviour is pinned by the integration suite
   and the browser suite. The layering is pinned by
   `cmd/api/architecture_test.go`, which fails on any of:
   - an import or database access that crosses a boundary above;
   - a transport (Gin, gRPC, the generated protos) imported by a service, the
     database layer or infrastructure — `core/shared` may use Gin, never gRPC;
   - a token signed outside `core/auth/service`;
   - a token verified without an audience;
   - an Owner scope built outside the Owner controller;
   - `alora-auth-go` importing App Central.

## 3. Request lifecycle (middleware order is semantic)

```
request-id (uuid) → request logger    (every later log line carries reqId)
  → recovery                          (panic → 500 envelope with reqId, logged with its stack)
  → error handler                     (renders every error recorded by later handlers; never leaks internals)
  → security headers                  (CSP default-src 'none', COEP/COOP/CORP, no-referrer; HSTS 1y preload in prod)
  → /.well-known CORS                 (ACAO * for discovery and JWKS only; nothing else answers another origin)
  → body limit                        (64 KiB)
  → global rate limit                 (per address; the server-to-server OAuth endpoints are exempt, limited per client)
  → text guard                        (a NUL or bytes that are not UTF-8 in the path or query → 400)
  → under-pressure                    (heap/RSS over its ceiling → 503 + Retry-After: 10 on every route)
  → [route]
       /.well-known, /health: public
       /oauth/authorize: the session cookie
       /oauth/token|revoke|introspect: failed-authentication budget (per address)
                                       → per-client budget → client_secret_basic
       /auth/*: SameOriginOnly (state-changing requests) + a per-route limiter
       /api/*: Authenticate("app-central") → RequireFresh (the session gate, once per request;
               flags a stale token)
         /api/admin/*: RequireScope(the route's scope)
         /api/owner/*: RequireOwner(12h); company writes check X-Alora-Target-Company
```

The gRPC door (`GRPC_PORT`; off when unset) runs the same stages as interceptors:

```
request-id (fresh, never the caller's) → recovery → log (method, code, duration, address)
  → under-pressure                    (→ UNAVAILABLE)
  → failed-authentication budget      (per address)           ┐ the very limiters
  → per-client budget                 (address + client id)   ┘ /oauth/token uses
  → TokenService.GetToken             (client_secret_basic in the `authorization` metadata)
```

Signed cookies are verified where they are read (refresh, logout, the federated
callbacks, the company chooser), not by a middleware. Under-pressure reads the
memory counters at most once a second — the read stops the world, so it never
runs per request. A shed request costs no authentication and no handler, and
`/health/pressure` reports the same counters for a load balancer.

**The login token is a snapshot; the database decides.** `RequireFresh` loads
the caller — session, user, company, scopes, Owner — from the database on every
request, and compares the versions it read (`admin_version`,
`permissions_version`) with the token's `av` and `pv`. When they differ, the
request is still decided from the database, and the response carries
`X-Alora-Token-Stale: 1`; the SPA then refreshes once (one renewal shared by
every request that saw the flag) and reloads `/api/me`.

**CSRF is refused three ways, independently:**
1. The session cookie is `SameSite=Lax`, so no cross-site POST carries it.
2. Every JSON endpoint refuses a body that is not `application/json`, which a
   cross-site form cannot send.
3. `SameOriginOnly` refuses a state-changing `/auth` request unless Fetch Metadata
   (else `Origin`) says it came from App Central's own origin. This one also
   stops a same-*site* sibling subdomain, which SameSite does not.

`/api/*` is Bearer-only; no ambient credential authorizes it.

## 4. Security architecture

> Every control below maps to an explicit invariant in `SPEC.md §2` and a threat
> in §9 of this doc.

### Tokens (three kinds)
- **The login token** (`aud: app-central`, `typ: at+jwt`, 15 min) is the only
  token `/api/*` accepts. It says who and in which company (`sub`, `tenant_id`,
  `email`), which session (`sid`), and everything about their App Central
  access as a **snapshot**: `scope` (the scopes held — each edit scope alongside
  its read — plus `owner` for an Owner), `products` (the keys of the apps they
  may open; no roles) and `av`/`pv`, the versions the snapshot was taken at. The
  snapshot is for the SPA to render; no request is authorized from it (§3).
- **A person's product token** (`aud: product:<key>` only, `typ: at+jwt`, 15 min,
  `principal: user`) carries the roles in that one product, the product as
  `client_id`, and its own product-login `sid`. It is minted only through the
  code flow and re-minted at each refresh from the current state of the
  database.
- **An application's product token** (`aud: product:<key>` only, `typ: at+jwt`,
  15 min, `principal: client`, no refresh token) is minted by the
  client-credentials grant: `sub` = `client_id` = the API client, its company as
  `tenant_id`, the `scope` it asked for out of its own, `roles: []`, and as `sid`
  the secret it was issued under. No person, no email.
- **ID tokens** (`typ: JWT`, `aud: <product id>`) carry the nonce, `auth_time`
  and App Central's `sid`.
- **RS256 only.** The verifier pins the algorithm, resolves the key by `kid`, pins
  `typ` and requires the audience. One signer plus verify-only keys make rotation
  overlap safe, and all of them are published in the JWKS.

### Sessions and refresh-token rotation (the crown jewels)
- A sign-in opens a **central family**; each product login is a **product family**
  under it. Refresh tokens are opaque (hex), stored as `sha256` hex. Rotation runs
  in a pgx transaction with `SELECT … WHERE refresh_token_hash=$1 FOR UPDATE`, with
  no `revoked_at` filter, because it must see revoked rows.
- **Each rotation is a fresh decision.** The gate is re-read every time: family,
  parent, user, company, product, subscription and access. So is the login
  policy. Lost access revokes the product family (`ACCESS_LOST`); a policy that no
  longer allows the sign-in revokes the tree (`POLICY`).
- **Reuse detection.** A replay outside the 30 s grace window revokes — for a
  central token, the tree; for a product token, that product's login — and
  returns 401. The revocation is **committed before returning** (D1).
- **Grace race.** A benign concurrent rotation returns **409** (keep the cookie,
  burn nothing). The SPA refreshes with `keepalive` requests (D28), so a page left
  mid-refresh still stores the new cookie, and the retry succeeds.

### Authorization and tenant isolation
- **Scopes.** Every `/api/admin` route needs one App Central scope — `…:read` to
  look, `…:edit` to change (SPEC §2 has the table) — held through the person's
  groups, extras given to them alone, or the system group `ADMINS`, which holds
  every scope. They are read from the database on every request.
- **Two rules keep delegation from becoming escalation**, checked in the
  services (`shared.Scope.CanGive`, `CanManage`) on every path that changes App
  Central access:
  1. nobody gives or takes away a scope they do not hold — a group's scopes,
     creating or deleting a group, membership (`ADMINS` included), invitations,
     extras;
  2. nobody acts on someone with more access than they have, and nobody but an
     Owner acts on an Owner. Access here is **reach**: the scopes held plus those
     of the groups a person manages (`vw_ScopeReach`, which grants nothing).
- **Group managers** add and remove one group's members and nothing else. A
  `groups:edit` holder who holds everything the group gives (or the Owner)
  appoints them; never oneself, never on the Admins group. Their door,
  `/api/me/managed-groups`, is not a scope: the database is asked on every call
  whether they manage that group, and again inside each write, under a share
  lock on the group row that dismissal locks for update. They never change the
  membership of the group's managers, themselves included.
- **The Owner** is in `tbl_platform_owners` (the app role cannot write it), is
  bound by neither rule, must have signed in within 12 h, and must repeat the
  target company in a header on every write. Each Owner action is audited in the
  platform company and in the target company.
- **Product access** is direct grants ∪ group grants, from the product's role
  catalogue, counting only for an active product, a live subscription and an
  active company, and only the Owner changes it. A change bumps the affected
  users' `permissions_version`, and a change to their App Central access their
  `admin_version`, inside the same procedure as the change.
- **Tenant isolation is enforced twice:**
  1. *Application:* every tenant-scoped query filters by the scope's
     `client_id`, never a body- or param-supplied one; another company's
     resource answers 404.
  2. *Database:* composite foreign keys `(…, client_id)` make a cross-tenant row
     physically unrepresentable.

### Applications: API clients and client credentials
- **An API client** belongs to one company and has one scope list (where its
  tokens may be used: `api:*`, `grpc:*`, `mcp:tools`), one product list, and up
  to **two live secrets** (`acc_…`, SHA-256 at rest, shown once), so a secret
  rotates without downtime. Only products the Owner has switched to accept API
  clients, and that the company is subscribed to now, can join a list.
- **Client authentication is one path for both kinds.** One lookup
  (`vw_OAuthClientCredential`) returns a product's secret or an API client's
  live ones; the presented secret is hashed once and compared in constant time
  with every stored hash, or with a dummy when there is none; every failure is
  the same `invalid_client`. Only then does the kind matter: a product may use
  the code flow and refresh, an API client `client_credentials` alone.
- **A token is for one product**, named by `resource=product:<key>`. The grant
  (`vw_ApiClientGrant`) is checked at every token: the client and its company
  on, the product on the list, still accepting API clients and subscribed. Any
  miss is the one `invalid_target`, so a client learns nothing about products it
  was not given; a scope it lacks is `invalid_scope`.
- **Introspection** reports an application's token active only while that grant
  still holds, every scope in it is still the client's, and the secret it was
  issued under is live — so revoking a secret ends its tokens at every product
  that introspects.

### gRPC
- Off unless `GRPC_PORT` is set. In production the listener serves TLS itself or
  declares a TLS-terminating proxy (`GRPC_BEHIND_TLS_PROXY`); anything else stops
  the boot.
- The interceptors mirror the HTTP chain (§3), and the rate limits are the token
  endpoint's own limiters: a budget spent through one door is spent for both.
- 64 KiB messages, 64 streams per connection, a 10 s handshake, idle and maximum
  connection ages, ping enforcement; the health service; reflection only outside
  production. Status codes carry the OAuth error as `ErrorInfo.reason` (domain
  `auth.alora.io`).

### Sign-in
- **Identifier-first.** Discovery answers by domain, so it reveals no account.
  Password sign-in checks up to ten live accounts holding the address, runs a
  dummy verify when none exists, and shows a company list only after the password
  was right.
- **Login policies** (user → highest-priority group → company default) are
  enforced at the end of every path — a right password on an SSO-only account is
  the same 401 — and again at every refresh.
- **Google and company SSO** share one OIDC client, whose checks are in SPEC §2.
  Federated sign-in never creates an account; linking rules are in SPEC §2.
- **Launch** is OIDC third-party-initiated login: App Central opens the product's
  `initiate_login_uri`, and the product's backend starts its own request. No
  unrequested code is ever delivered.

### Crypto primitives
- **Passwords:** argon2id, `m=19456 KiB, t=2, p=1, salt=16B, key=32B`. Verify
  swallows all errors → `false` (never 500). Max length 512 UTF-16 code units. The
  unknown-user path still verifies against a startup `DUMMY_HASH`, which makes
  the anti-enumeration constant-time.
- **Opaque tokens:** refresh = `rand(32B)→hex`; codes, reset and invite tokens,
  state and nonce = `rand→base64url` (unpadded); product secrets `acs_…`, API
  client secrets `acc_…` (the first 12 characters kept in the clear, to tell two
  apart). At rest every one is `sha256` lowercase hex.
- **PKCE:** S256 only; `base64url(sha256(verifier))` compared with
  `subtle.ConstantTimeCompare`.
- **SSO secrets:** AES-256-GCM (`secretbox`), key from `SSO_SECRET_KEY`,
  associated data = the connection id, so a sealed secret cannot be moved to
  another connection.
- Single-use redemptions (codes, invitations, resets, sign-in states) are single
  atomic statements, with no check-then-act race.

### Cookies
- `alora_cs` (the session), `alora_login` (a federated round trip, signed) and
  `alora_choose` (a company choice, signed). All are HttpOnly, `SameSite=Lax`,
  `Path=/`, **host-only**, `Secure` and `__Host-`-prefixed in production.
- No cookie carries an access token, and none is shared with another host.
  Clearing replays the exact attributes.

### Perimeter
- **CORS:** only `/.well-known/*` answers another origin (`*`, no credentials).
- **Rate limiting:** fixed-window counters. Globally 100/min per address;
  password sign-in per address+email (`RATE_LIMIT_AUTHORIZE_IP_MAX`). The fixed
  budgets (per minute unless noted):

  | Route | Budget |
  |---|---|
  | discovery | 60 |
  | company choice | 20 |
  | refresh and logout | 60 |
  | federated | 30 |
  | authorize | 60 |
  | server-to-server OAuth (HTTP and gRPC) | 600 per client id and address |
  | failed client authentications (HTTP and gRPC) | 20 per 15 min per address |
  | accept-invitation and reset | 10 per 15 min |
  | lookup | 20 per 15 min |
  | change-password | 5 per 15 min **per account** |

  `RATE_LIMIT_SCALE` scales them. `SetTrustedProxies` is an explicit env
  allowlist — Gin's trust-all default would let clients spoof addresses — and
  the gRPC door believes `x-forwarded-for` only from the same proxies.
- **Security headers:** strict CSP, HSTS with preload (production only),
  COEP/COOP/CORP, no-referrer.
- **Outbound (OIDC):** in production https only, private addresses refused at
  dial time, 1 MB / 10 s limits, no redirects, no proxy.

### Input validation
- `json.Decoder.DisallowUnknownFields()` → unknown fields are **rejected (400)**;
  a non-JSON body is 415. `return_to` is followed only when it is a path on App
  Central (`shared.SafeReturnTo`, mirrored in the SPA).
- **Text the database cannot store** (a NUL, bytes that are not UTF-8) is refused
  at every edge it can arrive through — the text guard for paths and queries,
  `BindJSON` for bodies, the OAuth controller for forms and Basic credentials,
  the gRPC handler for its fields — with `shared.Storable` as the one rule, and
  PostgreSQL's own refusal (22021, 22P05, and 54000 for a value too large for
  its index) mapped to 400 as the backstop.
- **A value is judged by the text that will be stored.** A format rule carries
  its length (`fqdn` alone would take a domain of any length, which a unique
  index cannot hold), and `shared.AbsoluteURL` reads a URL's raw text as well as
  its parse: `url.Parse` lower-cases the scheme and leaves the fragment of a lone
  `#` empty, where the tables' checks (`^https?://[^#]+$`) read the text. The
  tables hold the standards' lengths as CHECKs: a domain 253, a provider's
  subject 255.
- **A name is never blank.** Every name — a company's, a group's, an API
  client's, a product's, a policy's, an SSO connection's — carries `notblank`
  (registered in `BindJSON`): one that trims to nothing is refused like no name,
  though `min=1` would count its spaces.
- **A browser's identity is kept, not judged.** It is display-only, and HTTP lets
  a header carry bytes that are not UTF-8, so `shared.StorableText` makes it
  storable (U+FFFD, no NUL, 512 bytes cut at a character boundary) instead of
  refusing the sign-in it arrives with.
- **A parameter given twice is refused** at `/oauth/authorize` as at the token
  endpoint (RFC 6749 §3.1): which copy counts is never something App Central and
  a proxy in front of it can disagree on. A repeated `client_id` or
  `redirect_uri` is a 400 shown here; any other parameter it reads, an
  `invalid_request` sent back to the product.
- **An identity provider's claims are input.** A subject past OpenID Connect's
  255 characters, or one the database cannot store, fails the exchange; an
  address past 320 characters, or holding a NUL, counts as none.
- **A check followed by a write is never the rule's only guard.** Uniqueness is a
  unique index (a live invitation per address is `UQ_tbl_invitations_client_email_pending`),
  a limit is a row lock, and a write whose target vanished a moment ago (a group
  deleted while someone joins it) maps its foreign-key violation to the client's
  404 or 400.

### Secrets & audit
- **Fail-fast config.** Required and retired variables are checked at boot. In
  production placeholder secrets are rejected, `COOKIE_SECRET` must be at least
  32 bytes, the origins must be https, and `SSO_SECRET_KEY` is required.
- **Log redaction is a security control:** auth, cookie and set-cookie headers
  and secret body fields (passwords, codes and verifiers, access, refresh and ID
  tokens, client secrets) are redacted, and pgx query logging is OFF (queries
  carry hashed tokens). The gRPC log line never includes metadata or messages.
- **Audit is append-only, and enforced rather than assumed.** The application role
  holds `INSERT` only, and the actor foreign key is `ON DELETE RESTRICT`, so a
  user with history cannot be deleted. Written fire-and-forget on a detached
  context, so it can neither block nor fail a request. A change to an API client
  records what changed — its scope, its products, a secret's prefix, never a
  secret.

## 5. Data layer

- **pgx/v5 + pgxpool** behind one `DbContext` (`internal/database/contexts`).
  Feature services never see the pool: they call the table services, built from
  the DbContext or from the `TxContext` that `Begin` returns for transactional
  flows. Those flows are rotation, sign-in, invite acceptance, password change,
  group writes and bootstrap.
- **sqlc** generates one shared `Querier` from `../alora-auth-db/api`, whose
  every statement is a `CALL stp_…` or a `SELECT … FROM udf_…`. There is no SQL
  statement in this repository, so a procedure-signature change is a compile
  error here rather than a runtime failure. Enum parameters are cast at the call
  (`::"Type"`), so no connection-time type registration is needed. All id columns
  are `TEXT` (→ Go `string`).
- **Schema and procedures** live in `../alora-auth-db`, one file per object, each
  produced by a byte-reproducible generator (`gen_*.py`), which also refuses a
  constraint or index name longer than PostgreSQL's 63 characters. Its
  idempotent `build.sql` applies them and refuses a v1 or v2 database outright:
  schema v3 is rebuilt, not migrated.
- **Invariants the database enforces**, beyond the tenant foreign keys:
  - exactly one `ADMINS` group and one default policy per company;
  - unique policy priorities per company;
  - SSO domains unique, and never another company's verified domain;
  - Owners only in the platform company;
  - soft-delete-aware partial unique indexes on `lower(email)`, `lower(domain)`
    (verified only) and `lower(name)` per company;
  - scopes only from the closed catalogue `tbl_scopes`, each grant pinned to its
    kind — a person's (`tbl_group_scopes`, `tbl_user_scopes`) or an
    application's (`tbl_api_client_scopes`);
  - an API client's products only among its company's subscriptions; its
    secrets out of the app role's reach except to stamp `revoked_at` and
    `last_used_at`, and at most two live (under a row lock in the procedure that
    makes one).
- **Time/typing landmines:** the table services convert every nullable column to
  a nil pointer (`TimePtr`, `StringPtr`, …), so nothing above them can read a
  zero value where NULL was stored.

## 6. Cross-cutting operations

- **Configuration:** 12-factor env. No config file. `internal/config` is the
  single validated source; `.env.example` documents every variable, and a test
  keeps the two in step.
- **Observability:** structured slog (text in dev, JSON in prod). Health
  endpoints: `/health` (liveness), `/health/ready` (SELECT 1) and
  `/health/pressure` (heap 500 MB / RSS 600 MB).
- **API documentation:** Swagger UI and the OpenAPI 2.0 document at `/docs`,
  generated from handler annotations by [swag](https://github.com/swaggo/swag).
  They are served from assets compiled into the binary (no CDN), and
  `DOCS_ENABLED` gates them: default on outside production, off in it.
- **Background jobs:** `time.Ticker` goroutines started only once the listener is
  bound. Sessions and families past their caps are expired hourly, invitations
  every 6 h, codes hourly, sign-in states every 15 min. Each sweep is bounded and
  retried at the next tick; the shutdown signal stops them.
- **Concurrency:** handlers are synchronous. The only goroutines are audit/email
  (fire-and-forget, detached, each with `recover()`), the job tickers, and the
  two servers' own.
- **Errors:** `≥500 → {error:"Internal Server Error", reqId}` (never leak);
  `4xx → {error:label, reqId}`; `23505 → 409`; validation → 400; the OAuth
  endpoints answer RFC 6749 error objects, and gRPC a status code with the OAuth
  error as `ErrorInfo.reason` (an internal fault is `Internal`, never its text).
- **Graceful shutdown:** SIGINT/SIGTERM → the jobs stop, both servers stop
  accepting and drain in-flight calls within one 15 s budget (gRPC calls still
  running then are cut off), then the pool closes.

## 8. Deployment

Single static binary, env-configured, behind a reverse proxy (set
`TRUSTED_PROXIES`) that serves App Central's SPA and routes `/api`, `/auth`,
`/oauth`, `/.well-known` and `/health` to it on **one origin**. Products may live
on any domain; giving the auth host its own registrable domain keeps sibling
subdomains out of its site.

The gRPC door, when enabled, is a second port (`GRPC_PORT`) of the same binary:
TLS on the listener (`GRPC_TLS_CERT`, `GRPC_TLS_KEY`), or behind an HTTP/2
proxy that terminates it (`GRPC_BEHIND_TLS_PROXY=true`, with the proxy in
`TRUSTED_PROXIES` so its `x-forwarded-for` is believed).

Sign-in state is in the database, so replicas are correct. Rate-limit counters
are per process by default, on both doors — so N replicas grant N× the budget.
Setting `RATE_LIMIT_STORE=database` moves the brute-force-sensitive budgets
(password sign-in, the token endpoint, failed client authentications and
per-account password change) into a shared counter table
(`tbl_rate_limit_counters`, an atomic upsert under the row lock), so every replica
draws on one budget; the other, lower-risk budgets stay per process. The shared
store fails open — a database error allows the request rather than 429-ing the
whole fleet — and a background sweep deletes expired counters.

## 9. Threat model → controls

| Threat | Control |
|---|---|
| JWT algorithm confusion | RS256 pin + kid resolution + `typ` pin; reject none/HS256/unknown kid |
| A token used where it does not belong | Mandatory audience: App Central's token only at `/api`, each product's only at that product; `principal` tells a person's product token from an application's; introspection answers only about the caller's own tokens |
| Acting on a stale token | The database decides every request; the token's `av`/`pv` only flag a stale snapshot (`X-Alora-Token-Stale`) |
| Refresh token theft / replay | Family rotation + reuse detection (tree or product burn), `FOR UPDATE`, committed revocation |
| Stolen session outliving a change | Every rotation re-checks sessions, user, company, access and policy |
| Code injection / planted codes | Launch by third-party-initiated login; codes bound to client, redirect URI, PKCE, nonce and session; replay revokes the login |
| Open redirect | Exact redirect-URI match before any redirect; `return_to` paths only (server and SPA) |
| Cross-tenant data access | Scope `client_id` in every query **+** composite FKs at the DB |
| Privilege escalation | Scopes and Owner read from the DB per request; rule 1 (give or take away only scopes you hold) and rule 2 (manage only people with no more reach; only an Owner acts on an Owner); product access the Owner's alone; Owners only via bootstrap; recent sign-in + target header for Owner writes |
| A group manager escalating | Appointing needs everything the group gives (rule 1) and rule 2; nobody appoints themselves (service + CHECK); no managers on the Admins group; managers never change managers' membership, their own included; managership re-checked inside each write under the group row's lock |
| User/account enumeration | Identical 401s + dummy-hash verify; discovery by domain; company list only after the first factor |
| Password cracking / guessing | argon2id (19456/2/1); per ip\|email sign-in limit; per-account change-password limit |
| CSRF (incl. same-site siblings) | SameSite=Lax + JSON-only + SameOriginOnly on `/auth`; Bearer-only `/api` |
| Hostile identity provider / SSRF | Issuer equality, RS256 + JWKS, iss/aud/azp/nonce; https-only, private-address refusal, size/time caps in production |
| Session fixation / login CSRF on callbacks | State + nonce + PKCE bound to the browser by a signed, single-use cookie and a DB row |
| Stolen SSO secret at rest | AES-256-GCM with the connection id as associated data |
| Stolen application secret | SHA-256 at rest, shown once, optional expiry, at most two live, revocable; its tokens last 15 min with no refresh, and introspection reports them inactive once the secret is revoked |
| Guessing client secrets / probing client ids | Constant-time comparison against every stored hash or a dummy; one `invalid_client` for every failure; a per-address failure budget shared by HTTP and gRPC |
| An application reaching a product it was not given | Only listed products that accept API clients, checked at every token and every introspection; one `invalid_target` for any miss; scopes only from its own list |
| Plaintext gRPC in production | The boot refuses it unless TLS or a TLS-terminating proxy is configured |
| A product accepting a forged or misdirected token | The Go helper's `Verifier` (RS256 pin, issuer, audience, `typ`, expiry; keys through a discovery document whose issuer must match); its interceptors refuse a method with no rule |
| Injection | 100% parameterized via sqlc; no string-built SQL |
| Mass-assignment / unknown fields | DisallowUnknownFields → 400 |
| IP spoofing → rate-limit bypass | Explicit trusted-proxy allowlist, on both doors |
| Secret leakage in logs or responses | Redaction handler; pgx query logging off; hashes and sealed secrets never rendered; a product's or an API client's secret shown once, `no-store` |
| Weak/placeholder secrets in prod | Fail-fast startup validation |
| Audit tampering | Append-only role grant + RESTRICT actor FK |

## 10. Decisions

- **D13 — `timestamptz` over `timestamp(3)`.** All timestamp columns use
  `timestamptz` to eliminate the UTC/expiry ambiguity of the original
